{# Blocking overlay for saves that trigger a restart on the manager side. Included by the pages whose forms write ossec.conf, decoders, rules, mail settings or rsyslog files - all of which restart something afterwards so the change actually takes effect. That restart is slow enough to be worth explaining rather than just waiting through: Wazuh does not hot-reload configuration, so every one of these is a real service bounce, not a signal or a file watch, and this deployment's modest memory (docs/architecture/system-overview.md) makes a manager restart in particular take noticeably longer than the "a few seconds" a restart normally is. A plain POST with no feedback looks indistinguishable from a hung page for the whole duration, and without the reason an operator has no way to judge whether a bad experience is "still working" or "actually stuck." Two restart scopes exist and they are not the same wait, so the copy is not either: - full manager restart (the default) - wazuh-manager AND postfix, always both (services/ssh_transport.py's restart-services.sh has no way to restart one without the other). This is the slow one. - rsyslog only (data-restart-scope="rsyslog" on the three rsyslog forms in pipeline.html) - config-router-wrapper.sh's rsyslog branch restarts rsyslog itself and returns without touching wazuh-manager or postfix at all. Showing the manager-restart copy here would be wrong, not just imprecise - it names services this save never touches. It is deliberately non-dismissable: the request is already in flight and nothing the operator does here can cancel it, so offering a close button would only invite them to navigate away mid-restart and lose the result. The browser removes it on its own when the response arrives and the page navigates. #}

Applying changes

Wazuh does not apply configuration changes live, so this restarts the Wazuh manager and Postfix together. That is normally under a minute; this manager runs light on memory and can take longer under load. Leaving this page will not stop it.

{# The behaviour ships with the markup deliberately. This lived in static/js/app.js first, which was wrong in a way that looked right: app.js is the alert console's own script - polling, chart, table - and neither Pipeline nor Alerting loads it. The listeners never attached and the overlay never appeared, while everything about the markup and CSS checked out. Keeping the two together means a page that includes the overlay cannot end up without the code that shows it. #}
